# SOP: Running Batch Processing

## Overview

The batch runner processes multiple questions from the KQAPro or SciQA validation datasets and generates detailed results with accuracy metrics. You can either sample questions on-the-fly or use pre-generated questionnaire files for reproducible benchmarks.

---

## Prerequisites

1. Databases running (`docker compose up -d` in `db/`)
2. Qdrant populated (`python db/populate_vector_db.py` for KQAPro, `python db/populate_sciqa_vectors.py` for SciQA)
3. Validation dataset downloaded (`db/datasets/kqapro/val.json` and/or `db/datasets/SciQA/`)
4. `.env` configured with API keys
5. `config.toml` configured with desired LLM provider

---

## Generating Question Datasets (Recommended)

For reproducible benchmarks across runs and experiments, use the question dataset generator to create standardized JSON questionnaire files.

### Generate Questionnaires

```bash
# Generate both KQAPro and SciQA questionnaires (100 questions each)
python db/generate_question_datasets.py --dataset both --n 100 --seed 42

# Generate only KQAPro questionnaire
python db/generate_question_datasets.py --dataset kqapro --n 100 --seed 42

# Generate only SciQA questionnaire (handcrafted source)
python db/generate_question_datasets.py --dataset sciqa --n 50 --seed 42 --sciqa-source handcrafted

# Generate SciQA with both handcrafted and autogenerated sources
python db/generate_question_datasets.py --dataset sciqa --n 120 --seed 42 --sciqa-source both
```

### Generator Arguments

| Argument | Default | Description |
|----------|---------|-------------|
| `--dataset` | both | `kqapro`, `sciqa`, or `both` |
| `--n` | 100 | Number of samples per dataset |
| `--seed` | 42 | Random seed for reproducibility |
| `--sciqa-source` | handcrafted | `handcrafted`, `autogenerated`, or `both` |
| `--output-dir` | db/ | Directory to save output files |

### Output Files

- `db/kqapro_questionnaire.json` - KQAPro questions with metadata
- `db/sciqa_questionnaire.json` - SciQA questions with metadata

### Questionnaire JSON Format

## Basic Usage

### Quick Test (10 questions, on-the-fly sampling)

```bash
python ama_kbqa/agents/kqapro_agent/batch_runner.py
```

### Using Pre-Generated Questionnaire (Recommended)

```bash
# KQAPro with questionnaire
python ama_kbqa/agents/kqapro_agent/batch_runner.py --questionnaire db/kqapro_questionnaire.json

# SciQA with questionnaire
python ama_kbqa/agents/sciqa_agent/batch_runner.py --questionnaire db/sciqa_questionnaire.json
```

### Custom Run (On-the-fly Sampling)

```bash
python ama_kbqa/agents/kqapro_agent/batch_runner.py \
    --n_questions 50 \
    --seed 123
```

### With LLM Judge

```bash
python ama_kbqa/agents/kqapro_agent/batch_runner.py \
    --n_questions 10 \
    --seed 42 \
    --postprocessing_mode llm_judge
```

### Limit Questions from Questionnaire

```bash
# Use first 5 questions from a 100-question questionnaire
python ama_kbqa/agents/kqapro_agent/batch_runner.py \
    --questionnaire db/kqapro_questionnaire.json \
    --n_questions 5
```

## LLM Judge Mode

When `--postprocessing_mode llm_judge`, each answer is evaluated for:

1. **Correctness** - Semantic equivalence to gold answer
2. **Argumentation Quality** - Logic and reasoning structure
3. **Score** - 1-5 rating
4. **Improvement Suggestions** - Actionable feedback

Judge configuration in `config.toml`:

```toml
[postprocessing]
judge_provider = "openrouter"
judge_model = "google/gemini-2.5-flash"
judge_temperature = 0.0
```

## Tool-Trace Few-Shot Example Export

After each batch run, **correct answers** with efficient tool usage (<=15 tool calls) are automatically exported as tool-trace examples to:

```
db/datasets/kqapro/fewshot-examples/
├── Count.json
├── Verify.json
├── QueryAttr.json
└── ...
```

Each example captures the abbreviated tool-calling sequence that led to a correct answer:

```json
{
  "question": "How many businesses managed by George Clooney have Dimension Films?",
  "answer": "0",
  "qtype": "Count",
  "trace": [
    {"tool": "FindNode", "args": "George Clooney", "result": "found Q7948"},
    {"tool": "GetRelationDetails", "args": "Q7948, manager_of", "result": "4 businesses"},
    {"tool": "RunSPARQL", "args": "COUNT with child_org=Dimension Films", "result": "0"}
  ],
  "lesson": "Used SPARQL for Count question after entity discovery.",
  "tool_count": 6,
  "collected_at": "2026-02-08T12:00:00"
}
```

Examples are sorted by efficiency (fewest tool calls first) and limited to 5 per question type. When injected into the agent prompt, only the top 3 are used. Use `--no-fewshot` to disable injection for ablation studies.

## Troubleshooting

### Agent times out

1. Check database connectivity
2. Reduce `max_iterations` if needed
3. Check for loop detection triggers in logs

### Low accuracy

1. Review `suggested_improvement` in judgments
2. Check if question types match strategies
3. Verify database has complete data

### High token usage

1. Consider using synthesis model with lower limits
2. Review tools being called (use GetNodeSummary instead of multiple GetAttributeDetails)
3. Check for loop patterns

### Memory issues

1. Process smaller batches
2. Agent uses `soft_reset()` between questions (preserves MCP connection)
3. MCP server is only closed at the end of batch (improves performance)

---

## Best Practices

1. **Use reproducible seeds** - Same seed = same questions
2. **Start small** - Test with 5-10 questions first
3. **Enable LLM judge** - Get quality metrics, not just accuracy
4. **Review failures** - Check console logs for debugging
5. **Export examples** - Build tool-trace few-shot database over time

## Multi-Model Benchmarking

For comparing multiple LLM models across both agents, use the dedicated multi-model benchmarking script.

### Overview

The `benchmark_agents.py` script tests multiple LLM models against KQAPro and SciQA agents using pre-generated questionnaires, providing:
- Leaderboards by accuracy, speed, and cost-efficiency
- Detailed per-question results with tool summaries
- Cost estimation based on token usage
- Resume capability for interrupted runs
- CSV export for analysis

| minimax-m2.1 | minimax/minimax-m2.1 | OpenRouter |
| glm-4.7 | zhipu-ai/glm-4.7 | OpenRouter |
| kimi-k2.5 | moonshotai/kimi-k2.5 | OpenRouter |
| deepseek-v3.2 | deepseek/deepseek-chat-v3-0324 | OpenRouter |
| gpt-oss-120b | openai/gpt-oss-120b:nitro | OpenRouter |
| qwen3-32b | qwen/qwen3-32b:nitro | OpenRouter |
| nemotron-3-nano-30b | nvidia/nemotron-3-nano-30b-a3b:nitro | OpenRouter |
| gpt-oss-120b-kit | gpt-oss:120b | KIT Ollama (`ki-toolbox.scc.kit.edu/ollama/v1`) |

### Usage

```bash
# Preview what would run (dry-run)
python -m ama_kbqa.benchmark_agents --dry-run

# Test single model on single agent with limited questions
python -m ama_kbqa.benchmark_agents --models minimax-m2.1 --agents kqapro --n-questions 3

# Full benchmark with CSV export
python -m ama_kbqa.benchmark_agents --export-csv

# Resume interrupted benchmark (skips completed runs)
python -m ama_kbqa.benchmark_agents --resume

# Custom timeout and output directory
python -m ama_kbqa.benchmark_agents --timeout 180 --output-dir ./my_results
```

### Answer Evaluation (LLM-as-Judge)

The multi-model benchmarking script uses **DeepSeek v3.2 as an LLM judge** to evaluate answer correctness. This provides semantic equivalence checking rather than simple string matching.

**How it works:**
1. For each predicted answer, the judge model receives the question type, question, gold answer, and predicted answer
2. The judge uses **JSON mode** (`response_format: {"type": "json_object"}`) for reliable parsing
3. Returns `{"correct": true}` or `{"correct": false}`
4. Automatic fallback to text parsing if JSON mode not supported by model

**Judge Evaluation Rules (Strict):**
- **INCORRECT** if: "I don't know", "unable to find", empty, or different fact than gold
- **CORRECT** only if: Same factual information (alternate names/formats OK)
- When in doubt, marks as INCORRECT (conservative)

**Important:** Judge token usage is **NOT** counted towards the benchmarked model's token count. The judge uses a separate API client.

**Judge Model Configuration** (in `benchmark_agents.py`):
```python
JUDGE_MODEL_CONFIG = ModelConfig(
    name="deepseek-v3.2-judge",
    provider="openrouter",
    model_id="deepseek/deepseek-chat-v3-0324",
    base_url="https://openrouter.ai/api/v1",
    api_key_env="OPENROUTER_API_KEY"
)
```

**Fallback Chain:**
1. Try JSON mode with `response_format: {"type": "json_object"}`
2. If JSON mode fails (unsupported), retry without it
3. Parse response as JSON, then fall back to text pattern matching
4. Last resort: rule-based string matching (exact, substring, yes/no equivalence)

### Features

- **LLM-as-Judge evaluation**: Semantic answer checking via DeepSeek v3.2 with JSON mode (tokens not counted)
- **Answer comparison**: Console shows both gold and predicted answers for each question
- **Progress bars**: tqdm progress bars with live accuracy/timing updates
- **Resume capability**: Skip already-completed runs based on existing output
- **Error recovery**: Continue on timeout or errors, log issues per question
- **Cost estimation**: Calculate approximate API costs from token usage
- **Average tokens**: Summary includes `avg_tokens` per question metric
- **Config override**: Dynamically switches LLM models at runtime via config cache

### Prerequisites

1. Pre-generated questionnaires exist:
   - `db/kqapro_questionnaire.json`
   - `db/sciqa_questionnaire.json`
2. `OPENROUTER_API_KEY` set in `.env`
3. Databases running for agent execution
